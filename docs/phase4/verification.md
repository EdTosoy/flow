4. **Schema changes.** Migration 003 adds eight processor tables: interpreter_version, payment, derivation, activity, settlement_batch, membership, evaluation and evaluation_activity. It adds one typed settlement normalizer registry/representation branch to Phase 3 and typed processor audit/outbox references. No prior financial/evidence row changes. 5. **Payment identity.** An opaque internal UUID uniquely associates `(source account, exact external payment reference)`. Scope inherits book/environment/provider/account. It groups multiple external records and is explicitly distinct from Phase 0's independently authorized internal payment intent. Cross-account identical references cannot collide.
6. **Processor activity model.** Immutable one-output derivations reference exact normalized revision/version. Capture, explicit fee, refund and chargeback each retain signed BIGINT contribution, currency, occurrence, payment association and optional external parent capture reference. Sign violations are stored as controls rather than rewritten.
7. **Lifecycle semantics.** Derived as-of activity population: observed, captured, partially_refunded, refunded, charged_back or under_review. No mutable flags. Chargebacks take precedence over refund lifecycle display without erasing either amount/history; any control failure yields under_review. Mixed currencies have NULL aggregate totals/currency.
8. **Fee semantics.** Many explicit fee activities per payment; zero fee allowed; fee evidence links to its own normalized record. Gross/net report difference never manufactures a fee. Fee reversals/adjustments need future supported source contracts/versioned interpretation, not silent reinterpretation.
9. **Refund semantics.** Multiple claims, including partial/full totals, reference captures in the same payment/scope/object-kind/currency. Per-capture cumulative valid refunds cannot exceed capture. Invalid external claims survive; all-or-none payment validation sets validRefundMinor to zero when controls fail. This is claim validation, not refund authorization or execution.
10. **Chargeback semantics.** Separate activity, parent/provenance and total. Never a refund. Source-specific dispute recovery, outcome and debit-ceiling/combined-refund rules remain deferred; no approved production chargeback policy is inferred.
11. **Settlement model.** Stable settlement identity is the scoped source fact; immutable batches represent report revision/normalizer/interpreter. Currency, reported net/time, transfer reference, declared count and provenance are explicit. No supplied period or departure/bank-arrival status is invented.
12. **Membership model.** Immutable ordered `(batch,ordinal)` source references support N:1 composition and unresolved activity identities. Repeated references remain evidence of duplicate membership; only distinct known components enter the diagnostic subtotal. Exact selected interpreted activities are frozen in typed evaluation links.
13. **Settlement calculation.** Signed exact component sum, with bigint/SQL NUMERIC aggregates and string output. Reported and calculated net remain separate. Incomplete/ambiguous/duplicate/cross-currency/invalid-sign population produces NULL full calculated net, retaining an explicitly diagnostic known subtotal. Even calculable claims can fail other controls.
14. **Processor-internal controls.** Missing/pending/ambiguous activities, ambiguous reports, duplicate/conflicting membership, currency/sign/parent errors, excess refunds, payment-control dependency and exact net mismatch. Sorted deterministic results. These are not bank reconciliation, accepted matching allocations or exception cases. Completeness means received itemized references were explained, not independent source/economic completeness.
15. **Interpretation/version strategy.** Explicit registered processor-v1 and retained migration/code/lockfile. Unique normalized revision + normalizer + interpreter identity. Unsupported interpreter rejected. Evaluation pins one activity normalizer and processor interpreter; alternative normalized outputs never become additive components. New interpretation meaning requires a new version and migration.
16. **Upstream correction behavior.** New source revisions produce new immutable derivations. Prior activities, reports, memberships, input snapshots, totals and controls remain byte-equivalent. Same evaluation key replays its original population; fresh keys evaluate new evidence.
17. **Ambiguous revision behavior.** Source tokens, timestamps, hashes and receipt order supply no authoritative ordering in this contract. Multiple revisions retain REVIEW_REQUIRED and no active selection. Monotonic-looking tokens 1/2 are deliberately not interpreted as ordering. Automatic supersession/review is deferred, with explicit ambiguity implemented now.
18. **Transaction boundaries.** Existing acquisition and normalization transactions remain separate. Processor derivation atomically commits association/activity or batch/all member evidence plus outbox. Evaluation separately commits consistent evidence snapshot, complete typed links and required failed-control audit. READ COMMITTED, shared source-account lock and stable snapshot helpers; no ledger/bank/external dual write.
19. **Concurrency behavior.** Twelve workers proven blocked in pg_stat_activity converge on duplicate derivation, related-activity payment identity and identical settlement membership. Competing settlement identities remain explicit conflicts on both evaluated batches. Concurrent excess refund claims cannot produce a valid excessive total; corrections committed while derivation waits leave selection ambiguous.
20. **Crash/retry behavior.** Accepted normalized evidence survives before derivation, injected failures after identity/activity/member/companion writes, and backend termination before COMMIT for both activity and settlement derivation. Actual TCP loss of successful COMMIT acknowledgement is exercised for derivation/evaluation; unchanged retry replays one result. Whole-command 40001/40P01 retries pass with bounded attempts and unchanged keys. SQLSTATE injections are not claimed as observed production deadlocks.
21. **Audit/outbox behavior.** Immutable provenance explains every pure interpretation; no per-activity acceptance audit noise. Failed control snapshots have one typed existing-schema audit event with actor, actual session principal, reason/version/time. Derivation has one existing-outbox processor.interpreted intent referencing exact immutable result/book. Deferred guards require companions. Replays add no companions. Publishers, consumers and supersession decisions remain deferred.
22. **Database constraints/functions/triggers.** Scoped association uniqueness; revision/normalizer/interpreter uniqueness; restrictive normalized/scope/payment FKs; amount/currency/sign guards; exact activity/batch/member projection guards; sealed populations; evaluated refund-bound CHECK; snapshot forgery rejection; complete selected-activity link population; companion scope/deferred commit guards; append-only UPDATE/DELETE/TRUNCATE protection; two restricted SECURITY DEFINER command routines and private snapshot/guard helpers.
