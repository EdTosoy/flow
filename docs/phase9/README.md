# Phase 9: completeness and independent financial controls

Scope: synthetic/test system-wide control coordination over existing Phase 1–8 evidence. Individual reconciliation matches prove relationships; they cannot prove everything expected was received. [Verification and completion report](verification.md), [ADR-015](../architecture/adr/015-versioned-financial-controls.md).

## Ownership, identity and scope

`@flow/control-domain → @flow/money` supplies exact contracts and deterministic partition/total/exposure rules. `@flow/control-postgres → @flow/control-domain + pg` supplies controlled resumable commands. Reviewed SQL composition reads source-owned coverage/processor/bank calculations and reconciliation/exception evidence; lower modules do not import controls. No new external dependency/version.

A command contains `bookId`, stable `runKey`, synthetic `actorId`, explicit `reconciliationRunIds`, version `financial-controls-v1`, `maxAgeSeconds` (default 86,400, range 1–31,536,000) and `createCases` (default false). Run IDs are sorted canonically; at most one run per mapping, all in the same book. Full payload, including actor/configuration, defines semantic identity. Conflicting key reuse rejects explicitly.

The root scope is **all received evidence in one book as of the frozen database snapshot**, not a calendar period or unseen obligations. Each result narrows to source account, acquisition batch/normalizer, processor settlement, bank statement, journal, allocation group or reconciliation mapping/run/side. Monetary results retain explicit currency; run/statement windows are retained without combining unrelated populations by date. Source environment/account/provider follows existing typed scope. Reconciliation exposure requires explicit population selection; missing mapping selection is UNKNOWN. Snapshots refuse more than 100,000 received raw records or 20,000 control inputs rather than truncating.

## Taxonomy and result meaning

Every result retains key/type, version through its run, scope, severity, unit, expected, observed, discrepancy, supporting evidence, evaluated time and frozen input. PASS means the **named assertion** is satisfied. FAIL means evidence proves a discrepancy/control breach. UNKNOWN means required evidence is missing, ambiguous, incomplete or unproven. No empty/missing expectation is fabricated as zero. Counts and seconds are labeled separately from monetary minor units.

| SOURCE                             | Reuse `ingestion.coverage`: independently supplied physical count/sequence vs raw receipts. PROVEN_COMPLETE → PASS; PROVEN_INCOMPLETE → FAIL; absent expectation → UNKNOWN. Raw identities, checksums, sequences and manifest/artifact checksums remain linked. Severity is named policy: ledger/allocation CRITICAL; source-period/freshness WARNING; other controls ERROR. Severity never changes status or financial truth. Intrinsic arithmetic can PASS while another intrinsic control FAILs: named assertions remain independently visible. Overall assurance is FAIL if any frozen result fails, otherwise UNKNOWN if any result is unknown, run incomplete, inputs changed or evaluation expired. Current PASS requires all those checks. Historical FAIL is retained when stale; it is not claimed to describe a fresh new population.

## Exact totals and exposure

Individual financial observations/exposure use existing Money bounds/currencies. Aggregates and discrepancies use PostgreSQL NUMERIC or TypeScript bigint, transported as canonical integer strings, including totals beyond individual BIGINT. Difference = observed − expected. Zero, missing expectation and unknown value are distinct. No PHP/USD mixing, FX, fee write-off or inferred accounting position.

Canonical exposure is financial evidence, **not exception counts**. For each explicitly selected mapping run:

- Fresh valid current allocation excludes its items regardless of operational state.
- Eligible unmatched item without counterpart: exact whole magnitude, once per stable item.
- Unique eligible wrong-amount pair: exact absolute residual, once per ordered processor/bank pair, even with two cases.
- Ambiguous/grouped/ineligible/invalidated or oversized residual: unknown component, never guessed value. Full exposure is null when any component is unknown. Explicit `knownUnreconciledMinor` and `knownAcceptedRiskMinor` diagnostic subtotals coexist with unknown/unknown-risk counts; they are never labeled complete totals. A proven nonzero known condition still makes the exposure control FAIL while the complete observed total remains null.
- Processor and bank claims lacking proven relationship overlap remain separate diagnostic `processorClaimMinor` / `bankClaimMinor`. When both occur, combined `unreconciledMinor` and `acceptedRiskMinor` are null, with explicit unknown overlap; they must not be added as economic loss. `pairResidualMinor` is separate.
- A stale/incomplete selected population cannot certify current totals: aggregate is unknown, original known subtotal/evidence retained diagnostically. New bank/source evidence requires a new selected reconciliation run.

Case IDs/current immutable event IDs supply accepted-risk metadata to the canonical component; they contribute no additional amount. Either side's risk acceptance labels one unique pair residual, counted once. `RESOLVED/ACCEPTED_RISK` stays unreconciled; no controls write allocation or report accepted risk as reconciled value. Closed unreconciled cases remain in aging. Book summaries retain currency and mapping scope instead of offering an unsafe grand total.

## History, stages, transactions and failure behavior

`controls.run`, `input`, `result`, `case_link` and immutable `version` registry live in migration 008; migrations 001–007 are unchanged. Inputs have restrictive typed source/batch/settlement/statement/run/group/journal FKs. Full frozen details retain raw/revision/member/candidate/entry/exception-event identities; underlying histories already forbid deletion/mutation. Mutable processing/current state is frozen as exact evidence, not read later as truth.

1. Create DRAFT under book lock and book/key uniqueness; same full command replays.
2. Freeze under REPEATABLE READ, book → sorted source locks → run lock. One coherent full population/manifest/hash/input set commits as SEALED. Guard recomputes the snapshot and deferred validation requires exactly that input set. A failed freeze leaves DRAFT.
3. Evaluate bounded 1–1,000 inputs under run lock, SEALED → EVALUATING. Results derive only from frozen inputs; unique `(run,key)` and SQL result checks prevent duplicates/forgery. Failed batches roll back; previous committed results remain resumable.
4. Complete under book/source/run locks, only after every input has one durable result. Optional generation/links, COMPLETED state, existing typed audit and outbox commit together. A failure leaves EVALUATING and no partial newly created cases/companions.

Run identity/configuration and sealed population are immutable; only listed state transitions are legal. Completed history, results, inputs, links and version semantics cannot UPDATE/DELETE/TRUNCATE. PostgreSQL constraints, immediate provenance/transition guards and deferred population/completion checks are final barriers. A narrowly privileged control login executes only stage/read routines, cannot directly mutate base tables, post journals or invoke reviewer commands. SECURITY DEFINER uses fixed `pg_catalog,pg_temp`; owners/superusers and trusted synthetic provisioners remain privileged boundaries.

Whole stages retry 40001/40P01 up to five attempts with unchanged identity/payload. A lost COMMIT response raises `UnknownControlCommit`; retry on a healthy connection resumes or replays existing durable state. No new key on retry, exactly-once delivery claim, scheduler or worker lease. Incomplete runs remain inspectable by state. Only completed evaluations produce audit/outbox; DRAFT/partial work is durable execution metadata, not a successful financial decision.

## Exception integration, summary and developer workflow

`createCases=true` applies only when a named SOURCE, PROCESSOR/PROCESSOR_TOTAL, BANK/BANK_TOTAL/BANK_COMPLETENESS, EXPOSURE, ALLOCATION or selected-run FRESHNESS control FAILs. Existing Phase 8 generation uses exact completed selected outcomes and lifetime mapping/item identity. Relevant failed results link existing/generated cases by source/mapping/group scope; repeated histories can associate the same case. A source-account result can link several affected unresolved items; a link is operational association, not proof that each item caused every failure.

Informational UNKNOWN and processing/ledger-only controls do not fabricate cases. Source/raw/ledger failures without mapped outcomes remain durable explicit FAIL results; generic control-subject case lifecycle is intentionally deferred. No dummy financial item or new reconciliation match is created. Existing case original evidence/history remains unchanged; new links are immutable. If case generation changes the operational snapshot after freeze, `current=false` correctly distinguishes as-of results from new case history.

`summary(id)` exposes states/time/version, current/as-of assurance, result/severity/status breakdown, each processing partition/backlog/failure, each reconciliation side/partition, scoped exact exposure/risk/unknown counts and failed-control case links. Result details retain oldest unreconciled age. This deterministic interface can feed a future dashboard; no UI or observability deployment.

```sh
pnpm controls run <control-command-json>
pnpm controls summary <control-run-id>
pnpm controls pipeline <public-input> <book-id> <run-key> <mapping-id> <from-UTC> <to-UTC> [--grouped]
```

`DATABASE_CONTROL_URL` is a separate provisioned synthetic control login. Pipeline reuses existing ingestion/processor/bank/reconciliation/exception runtime URLs and commands, then freezes/evaluates controls. Normal output has public runtime evidence only. Tests alone read private oracle truth after evaluation. Runtime modules/tools cannot import oracle or test harnesses; transitive manifest/Nx/import gates remain required.

Detectable simulator scope: supplied independent dropped-record counts, incorrect processor amounts/missing referenced activities, corrupted receipt dispositions, missing settlement/bank movements with interpreted counterparts, duplicate receipt non-duplication, pair/group ambiguity, independent bank closing inconsistency and accepted-risk exposure. Missing unseen obligations without independent source evidence remains UNKNOWN; no recall claim for all anomaly types or missing independent business/ledger authorization. No original generator/golden contract changed.

Deferred: generic raw/control-subject exception workflow, authenticated independent period closure/authoritative revisions, independent internal payment accounting orchestration, comprehensive receivable/in-transit/accounting-position equations, projections, FX/manual matching, production authorization/two-person approvals, scaling/streaming/soak, Phase 10 workers/publication, UI, real integrations, cloud and AI.
